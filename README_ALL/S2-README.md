# S2. Внешние вызовы больше не держат блокировку заявки и транзакцию (request-service)

Сервис: request-service. Миграция: **V5** (V4 занят идемпотентностью; если номера иные, возьмите следующий свободный).
Файлы накопительные: в них уже B5, B6, B7, B1 (часть 2), S5 и правки P1-10 не нужны, но B5 и P1-10 обязательны.

## Что было
Операции брали `FOR UPDATE` на строку заявки и в той же транзакции ходили в inventory, auth, catalog и warehouse
(таймауты 2 с и 10 с, до четырёх вызовов в выдаче). Медленный сосед держал соединение из пула (10 штук) и блокировку.

## Как теперь (три фазы, `RequestOperations`)
1. **Подготовка** (короткая транзакция): занять «аренду» операции на заявке (колонки `op_token`, `op_until`),
   проверить предусловия, снять данные для вызова в обычные объекты.
2. **Внешний вызов** без транзакции и без блокировок БД.
3. **Фиксация** (короткая транзакция): заблокировать заявку, убедиться, что аренда за нами, применить результат,
   снять аренду.
Пока аренда занята, любая другая изменяющая операция по этой заявке (в том числе сбор в комплектации) получает
**409 `OPERATION_IN_PROGRESS`**; чтение работает. Аренда истекает сама (60 с, для выдачи 120 с), если процесс упал.
Если аренда истекла и заявку занял другой запрос, фиксация даёт **409 `OPERATION_EXPIRED`**: внешний вызов мог сработать,
повтор подхватит его результат (ключи идемпотентности, подхват резерва и документа выдачи). Аренда хранится в БД,
поэтому работает при нескольких экземплярах сервиса.

## Что переведено
- `RequestService`: `review`, `reject`, `reserve`, `cancel` (в том числе резерв, отметки недобора и осиротевший резерв).
- `PickingService`: `create` (резервы из inventory и справочник работников), `addWorkers` (справочник работников).
  Остальные операции комплектации без внешних вызовов, но проверяют аренду после блокировки заявки (`lock`).
- `IssuingService.issue`: до четырёх вызовов inventory между транзакциями.
- `create`, `update`, `submit` заявки: каталог и склад запрашиваются до открытия транзакции (аренда не нужна: заявка
  новая или черновик владельца). Порядок проверок слегка изменился: ошибка номенклатуры может прийти раньше ошибки статуса.
- Остальные методы `RequestService` (`close`, `deleteDraft`, `readyForIssue`) берут блокировку через `lockAny`,
  который теперь тоже проверяет аренду.

## Проверить
- Фронтенд: код `OPERATION_IN_PROGRESS` показывать как «Идёт другая операция, повторите через несколько секунд»
  (кнопку не блокировать надолго); `OPERATION_EXPIRED` как «Операция прервана, повторите».
- `TransactionTemplate` инжектируется из автоконфигурации Spring Boot (один `PlatformTransactionManager`).
- Колонки `op_token`, `op_until` не добавлены в сущность `Request` (используются через JDBC), `ddl-auto: validate`
  это допускает.
- Сценарии: `scenario-5a`, `scenario-5b` (резерв, комплектация, выдача, отмена), затем вручную: вызвать `review`
  и сразу `pick` по той же заявке при остановленном inventory: `pick` получает 409, после таймаута всё освобождается.
- Нужен интеграционный тест на PostgreSQL (R15): параллельные `review` и `cancel` по одной заявке; один получает 409.

## Не сделано
- Те же вызовы под `@Transactional` в inventory-service (`ReceiptService.create/update/recommend/confirm`: каталог и
  warehouse внутри транзакции; `confirm` защищён только версией документа). Отдельный шаг.
- Резерв и выдача по-прежнему «почти ровно один раз» (M3): аренда защищает от параллельных операций, а не от
  сбоя между внешним вызовом и фиксацией; для этого остаются идемпотентные ключи и подхват.
