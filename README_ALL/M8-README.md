# M8. Даты приёмки и поступления назначает сервер; ввод пользователя стал справочной «датой накладной»

## Что было
`receivedAt` вводил пользователь, и по нему строился порядок FIFO при резерве: порядок выдачи можно было менять вводом даты.

## Что сделано (inventory-service)
- **Дата приёмки** `receivedAt` назначается сервером при создании и **заново при подтверждении** (`confirm`): она не бывает
  раньше сегодняшней даты в момент приёмки. Пользователь её не вводит и не меняет.
- **Дата поступления партии** (`batches.received_at`, по ней FIFO) берётся из даты приёмки документа, поэтому две даты
  всегда совпадают. Размещение позже подтверждения дату партии не меняет.
- **Дата накладной** `documentDate` (дата без времени): вводит пользователь, справочное поле, ни на что не влияет.
  В запросах на создание и изменение поле `receivedAt` заменено на `documentDate`; в ответах есть оба: `receivedAt`
  (дата приёмки, только чтение) и `documentDate`.
- Срок годности уже проверялся при создании, изменении и подтверждении (просроченный товар не принимается,
  «годен до» включительно); отдельно ничего не добавлено: при дате приёмки = сегодня срок не может быть раньше даты приёмки.
- Миграция `V13__receipt_document_date.sql`: колонка `document_date`; прежние значения `received_at` (их вводил
  пользователь) переносятся в неё. Если V13 занят, возьмите следующий номер.

## Файлы
`entity/Receipt`, `dto/InventoryDtos`, `service/InventoryMapper` (версия B1), `service/ReceiptService` (накопительная: S1, S2),
миграция V13.

## Известные нюансы
- Партия, которая приходит повторно (S1), сохраняет дату первого поступления: FIFO считается по партии.
- Фронтенд (ломающее изменение): в форме поступления поле «Дата» заменить на «Дата накладной» (`documentDate`, дата),
  показывать `receivedAt` как «Дата приёмки» только для чтения. Запрос с прежним полем `receivedAt` получит 400
  (строгий разбор JSON).
- Отчёты report-service строятся по событиям; поле `documentDate` в них пока не передаётся.
