# Пункт 2: ACCEPT_ACTUAL обходит проверки секции

## Что было
`resolve(ACCEPT_ACTUAL)` проверял только вместимость. Проверки статуса секции, «Нераспределено» и пригодности
(`requirePlaceable`, `requireSuitable`) выполнялись только при размещении работником. Между размещением и решением
кладовщика секцию могли заблокировать/заархивировать или изменить её правила, и товар всё равно проводился.
Строка остатка создавалась с `sectionBlocked=false` независимо от статуса секции.

## Что изменено (inventory, пакет `...inventory.service`)
| Файл | Изменение |
|---|---|
| StockPostingService.java | ACCEPT_ACTUAL: проверка, что секция та же, что записана в позиции (иначе 409 `ITEM_CHANGED`), склад, `SectionRules.requirePlaceable` на актуальном `SectionInfo`, затем вместимость. `post(...)` принимает `SectionInfo` и ставит `stock.sectionBlocked` через `SectionRules.blocksReservation`. Новый метод `placementItemForPlaced` (фактическое количество); общая часть вынесена в `buildPlacementItem` |
| PlacementTaskService.java | `resolve` для ACCEPT_ACTUAL вызывает `requireSuitable` для фактической секции и фактического количества (до транзакции, как в `confirmItem`) |
| SectionRules.java | Новый `blocksReservation(SectionInfo)` |
| SectionRulesTest.java | Два теста: `blocksReservation` и повторная проверка правил |

Файлы сохранены с CRLF, как в исходниках. Тесты не запускались (в среде нет Maven).

## Проверка
1. Работник размещает позицию в секцию X с расхождением (другое количество) -> DISCREPANCY.
2. Администратор блокирует секцию X.
3. Другой кладовщик (не тот, кто размещал) выбирает ACCEPT_ACTUAL -> 409 `SECTION_NOT_ACTIVE`, остатка и движения нет.
4. Вернуть секцию в ACTIVE, повторить -> проводится, `stock.section_blocked = false`.
5. Сузить правила секции (например, максимальный размер) так, чтобы позиция не подходила -> 409 `SECTION_NOT_SUITABLE`.
6. Обязательный тест из плана №6 (размещение в заблокированную/архивную секцию) стоит покрыть интеграционным тестом на Testcontainers.

## Остаётся (хвост B2)
- `SectionInfo` читается до транзакции проведения (TOCTOU): секцию можно заблокировать в промежутке между чтением и коммитом.
  Закрывается только событием о смене статуса секции, которое должно обновлять и строки остатка, созданные в этом окне,
  либо повторной проверкой статуса в момент проведения. Это отдельная задача вместе с TODO в `SectionService` (сужение ограничений).
- В ветке «Нераспределено» статус секции в `requirePlaceable` не проверяется: оставлено как есть.
