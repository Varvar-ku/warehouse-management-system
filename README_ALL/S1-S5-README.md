# S1 (партии) и S5 (зависший черновик выдачи)

Сервисы: inventory-service (S1) и request-service (S5). Новых миграций нет.

**База.** Архив рассчитан на состояние проекта после архивов B1 и B4/B6/B7 (они уже выданы):
- `StockPostingService` содержит и правки B4 (`REJECT_LINE`, статус `REJECTED`), поэтому B4 должен быть применён;
- `InventoryClient` содержит `release(requestId, marks)` из B1 (часть 2) вместе с новым `cancelIssue`.
Распаковывать в корень проекта с заменой.

## S1. Партия = (номенклатура, номер партии), повторная поставка пополняет её
Решение по умолчанию (вопрос 5 из анализа, подтвердите): одна партия может поступать несколькими документами и
храниться в нескольких секциях.
- `BatchLookup` (новый): поиск партии и строки остатка через JDBC + проверка совместимости (единица и срок годности).
- `StockPostingService.post`: под блокировкой по ключу партии находит существующую партию или создаёт новую; если в этой
  секции строка остатка уже есть, добавляет количество под блокировкой строки, иначе создаёт строку.
  Порядок блокировок: документ -> секция -> партия -> строка остатка.
- `ReceiptService.confirm`: номер партии больше не «занят». Отклоняются: повтор номера внутри документа, другая единица,
  другой срок годности относительно существующей партии (раньше этот конфликт всплывал уже после размещения).
  Срок годности у существующей партии не меняется (иначе поменялся бы порядок резерва по срокам).
- Партия сохраняет `receipt_id`, дату приёмки и снимок атрибутов первого поступления.
- Побочный эффект: если строка остатка «на проверке» (недостача, B1), добавленное количество тоже недоступно для
  резерва, пока кладовщик не решит недостачу (флаг относится ко всей строке).

## S5. Выдача: черновик больше не «зависает»
- `IssuingService.issue`: подтверждённый документ подхватывается, как и раньше. Оставшийся **черновик отменяется и
  создаётся заново** из текущих данных (получатель и комментарий текущего запроса теперь учитываются, свежие отметки
  недобора тоже). Черновик остаток не меняет, поэтому пересоздание безопасно. Проверка «ничего не собрано» выполняется до
  отмены черновика.
- `InventoryClient.cancelIssue(id, reason)` + `CancelIssueRequest` в контракте.
- `IssueService` (inventory) менять не потребовалось: его `cancel` уже есть.
- Не сделано: `issuedQuantity` по-прежнему берётся из собранного, а не из ответа inventory (в `IssueDto` нет количеств);
  проверка `issuedTo` (A4) остаётся на потом.
