# B4. Приёмка: тупик, если позицию нельзя разместить (inventory-service)

Распаковывать в корень проекта с заменой. Сервис: inventory-service. Миграция: **V10** (V9 занята B1).

## Что изменено
- Новое решение кладовщика `REJECT_LINE` (недостача, брак, потеря): позиция закрывается со статусом `REJECTED`,
  остаток и движения не создаются, комментарий обязателен (он уже `@NotBlank` в `ResolveRequest`).
- `REJECT_LINE` допустим и для позиции в статусе `PENDING` (товар сломан или потерян, работнику нечего подтверждать),
  поэтому подделывать расхождение не нужно. Остальные решения по-прежнему только из `DISCREPANCY`.
- Поступление уходит в `DONE`, когда каждая позиция `PLACED` или `REJECTED`. В событие `receipt.completed`
  добавлены `rejectedLines` и `placedLines`. Если отклонены все позиции, документ тоже закрывается `DONE` с нулевым приходом.
- `ReceiptService.cancel` не менялся: отмена по-прежнему запрещена, если есть `PLACED`. Часть позиций отклонена,
  остальные `PENDING`: отменить можно.

## Проверить
- Если в проекте есть миграция V7 (я её не видел), номер V10 остаётся верным; если нет, Flyway всё равно примет V10.
- Фронтенд: в диалоге решения по расхождению добавить «Отклонить позицию (недостача/брак)», статус `REJECTED` в `statuses.ts`.
- report-service: событие `receipt.completed` получило два новых поля, существующие потребители их игнорируют.

## Сценарий проверки
1. Поступление из двух позиций, задание на размещение. Первую разместить штатно.
2. Вторую отклонить: `POST /placement-tasks/{id}/items/{itemId}/resolve {"decision":"REJECT_LINE","comment":"Брак"}`.
3. Ожидается: позиция `REJECTED`, поступление `DONE`, остатка по второй позиции нет, в движениях одна запись `RECEIPT`.
