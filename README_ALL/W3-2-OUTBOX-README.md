# Волна 3, пункт 2: очередь outbox (M1)

## Что было
- Событие, которое не удаётся отправить (например, больше лимита размера), останавливало весь батч и все последующие события сервиса.
- Порядок шёл по `BIGSERIAL id`, а транзакции фиксируются в другом порядке: событие с меньшим id могло уйти позже большего.
- `FOR UPDATE SKIP LOCKED` при нескольких экземплярах перемешивал порядок.
- Транзакция БД держалась открытой, пока отправлялись сообщения по одному (до 5 с на каждое).

## Что сделано (common-lib: `OutboxRelay`, `OutboxAutoConfiguration`)
- **Порядок:** выбираются только строки завершённых транзакций (`tx_id < xmin` снимка), сортировка `(tx_id, id)`.
- **Один отправитель:** транзакционная advisory-блокировка, остальные экземпляры пропускают прогон.
- **Короткая транзакция:** все `send` запускаются подряд, затем ожидание подтверждений за общий срок 5 с. Успешный
  префикс помечается опубликованным одним UPDATE; при временном сбое остаток уйдёт в следующий прогон.
- **«Ядовитые» события:** постоянный отказ брокера (RecordTooLarge, ошибка сериализации, неверный топик) увеличивает
  `attempts` и пишет `last_error`; после `max-attempts` (10) событие запарковано, очередь идёт дальше.
  Временные сбои (брокер недоступен, таймаут) счётчик не трогают.
- **Мониторинг:** раз в минуту в лог WARN, если очередь не двигается дольше `stuck-warn-seconds` (60 с), и ERROR, если есть
  запаркованные события.

## Миграции (по одной на сервис, добавляют `attempts`, `last_error`, `tx_id`)
inventory V11, request V6, warehouse V3, auth V5, catalog V5. Номера выбраны как следующие за известными; **проверьте и
при необходимости переименуйте** (особенно warehouse: я знаю только V2). Auth и catalog требуют, чтобы их V4
(`outbox_event` из архива S4) был применён раньше. Если `wms.outbox.enabled=true` и в audit, report или notification,
им нужна такая же миграция (там я таблицу outbox не видел). Выкладывайте common-lib и миграции вместе: новый relay
использует новые колонки.

## Настройки (необязательные)
`wms.outbox.strict-order` (true), `max-attempts` (10), `stuck-warn-seconds` (60), `monitor-interval-ms` (60000),
`batch-size`, `poll-interval-ms`, `retention-days` как раньше.

## Важно знать
- `strict-order=true` зависит от `xmin` снимка PostgreSQL, который учитывает **все базы кластера**. Незавершённая
  транзакция где угодно (например, остановка в отладчике IntelliJ посреди транзакции) задерживает отправку outbox во всех
  сервисах, пока не завершится. Это видно по предупреждению монитора. Если мешает при отладке, поставьте
  `wms.outbox.strict-order: false` (вернётся прежнее поведение по `id`).
- Для запаркованных событий: разберите причину в `last_error`, исправьте и вернуть в очередь можно так:
  `UPDATE outbox_event SET attempts = 0 WHERE published_at IS NULL AND attempts >= 10;`
- Порядок гарантируется в пределах доставки в топик; один и тот же ключ идёт в одну партицию.

## Проверить
- Остановить Kafka на минуту: события копятся (`SELECT count(*) FROM outbox_event WHERE published_at IS NULL`),
  после запуска уходят по порядку, дублей нет сверх одного повтора.
- Вставить событие с огромным payload (больше `max.request.size`): оно запаркуется после 10 прогонов, остальные идут.
- Запустить два экземпляра сервиса: в логах отправляет только один.
