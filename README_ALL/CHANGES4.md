# Пункт 3: отмена из PICKING_WITH_SHORTAGE теряет собранное

## Что было
В `RequestService.finishCancel` собранный товар для события `picking.return_required` искался только в заданиях
NEW и IN_PROGRESS. После завершения сборки с недостачей (статус заявки PICKING_WITH_SHORTAGE) задание уже COMPLETED,
поэтому список «вернуть в секции» оставался пустым, событие не публиковалось, и о товаре, лежащем в зоне
комплектации, никто не узнавал. (Остальное из отчёта в вашей версии кода уже исправлено: READY_FOR_ISSUE входит
в `RESERVED_STATES`, а отметки недостачи в `prepareCancel` берут и COMPLETED-задания.)

## Что изменено
| Файл | Изменение |
|---|---|
| request/.../service/RequestService.java | `finishCancel`: выборка заданий включает COMPLETED; строки собранного берутся из всех трёх статусов; отклоняются (`reject`, событие `picking.task_rejected`) только открытые задания, завершённые остаются как есть. В `picking.return_required` добавлено поле `status` (статус заявки до отмены). Обновлён javadoc `cancel` |

RequestStatus, PickingService, репозитории, SectionService менять не потребовалось. Файл сохранён с исходными
окончаниями строк. Тесты не запускались (в среде нет Maven).

## Проверка
1. Заявка с двумя позициями, зарезервировать, собрать одну полностью, по второй зафиксировать недобор, завершить сборку
   -> PICKING_WITH_SHORTAGE.
2. Отменить кладовщиком с причиной.
3. В audit должно быть событие `picking.return_required` с строкой по собранной позиции и `status = PICKING_WITH_SHORTAGE`;
   задание сборки остаётся COMPLETED; резерв снят, недостача передана в inventory (отметки B1).
4. Отмена из PICKING с частично собранным (задание IN_PROGRESS) работает как раньше: событие, `picking.task_rejected`.
5. Отмена из READY_FOR_ISSUE при ненулевой сборке по-прежнему отклоняется (`CANCEL_NOT_ALLOWED`).
6. Тесты плана №3 и №4 (отмена в каждом статусе с проверкой резервов, недобор и повторный резерв) нужны на Testcontainers.

## Решение владельца продукта
Сейчас из PICKING_WITH_SHORTAGE с собранным товаром отменять можно (как и из PICKING), с событием о возврате.
Альтернатива, чтобы было как в READY_FOR_ISSUE («собранное не отменяется»): в `prepareCancel` расширить условие
`r.getStatus() == READY_FOR_ISSUE && !nothingPicked(...)` на PICKING_WITH_SHORTAGE. Тогда отмена после недобора
будет невозможна, пока что-то собрано, и останется только выдать собранное. Я выбрал первый вариант: он не отнимает
у кладовщика существующую возможность и не требует изменения тестов статусов.
Пока нет процесса возврата в секции (TRANSFER, S3), событие остаётся только сигналом для людей.
