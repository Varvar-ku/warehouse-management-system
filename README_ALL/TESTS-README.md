# Интеграционные тесты (R15)

Четыре набора, по порядку:

| Набор | Где | Что проверяет |
|---|---|---|
| Параллельный резерв | inventory: `ParallelReservationIntegrationTest` | 8 запросов по 3 на остаток 10 (частично): зарезервировано ровно 10, резерв не больше остатка, сумма резервов = `reserved_quantity`, ни одной ошибки сервера; 4 запроса «всё или ничего»: успешны ровно 3, зарезервировано 9 |
| Две приёмки с одной партией | inventory: `SameBatchReceiptsIntegrationTest` | размещение двух документов с партией B-1 одновременно (10 повторов): одна партия, одна строка остатка с суммой 10, два движения RECEIPT, оба документа DONE; другой срок годности: вторая приёмка отклоняется |
| Отмена заявки в каждом статусе | request: `CancelRequestIntegrationTest` | все 15 статусов × кладовщик и владелец: что разрешено, что даёт «Отмена недоступна»; чужой пользователь получает 404; снятие резерва вызывается ровно там, где нужно; недобор 5-2=3 передаётся в inventory; открытое задание отклоняется; READY_FOR_ISSUE без собранного отменяется, с собранным нет; сбой inventory оставляет заявку нетронутой и снимает аренду |
| Коды 401/403 по ролям | все пять сервисов: `RoleAccessIntegrationTest` | для каждого эндпоинта и ролей USER, STOREKEEPER, WAREHOUSE_WORKER, ADMIN, SERVICE: разрешённая роль не получает 401/403, остальные 403; без токена, мусор, просроченный токен, чужая подпись, чужой издатель: 401. Для inventory: запись резервов и выдач только со служебным токеном |

## Как устроено
- `IntegrationTestBase` (в каждом сервисе, пакет `...it`): настоящая PostgreSQL 18 в Docker (Flyway выполняет все миграции),
  полная цепочка Spring Security с настоящей проверкой JWT, `MockMvc`; Kafka и outbox отключены, `OutboxPublisher` заменён
  заглушкой. Без Docker тесты **пропускаются**, сборка не падает.
- `TestTokens`: токены, подписанные тем же секретом (`app.security.jwt.secret` задаётся в тесте).
- `RoleAccessTestSupport`: матрица доступа; в конкретном классе только список эндпоинтов.

## Зависимости (test) в pom.xml каждого сервиса
`spring-boot-starter-test` (скорее всего уже есть) и

    <dependency>
        <groupId>org.testcontainers</groupId>
        <artifactId>testcontainers</artifactId>
        <scope>test</scope>
    </dependency>

Версию управляет BOM Spring Boot. Используются только ядро Testcontainers (`GenericContainer`, образ `postgres:18`) и
`spring-test`; `spring-security-test` и модуль Testcontainers для PostgreSQL не нужны. Запуск: `mvnw test` (нужен Docker).

## Что стоит знать (тесты не запускались)
- Я не мог собрать и выполнить тесты: возможны опечатки в импортах и расхождения с вашими DTO. Проверьте в первую очередь
  тела запросов в матрицах: для эндпоинтов с `@Valid` тело должно быть корректным, иначе ответ 400 приходит раньше проверки
  прав и тест покажет «ожидался 403, получен 400» (это ошибка теста, а не прав). Тела для inventory (`write-offs`,
  `adjustments`, `shortages`), warehouse (`sections`), catalog и auth составлены по DTO, которые я видел.
- В матрице не покрыто: `PickingController` (request-service), `POST /placement/recommend|validate` и создание правил
  размещения (warehouse), `POST /auth/login` и `/me` (вход публичный, `/me` отвечает 401 для несуществующего пользователя),
  `/me/password` (теперь 403 по настройке), audit, notification, report, gateway.
- Эндпоинты `usage` (M4) и `documentDate` (M8) в тестах предполагают, что соответствующие архивы применены.
- Тест резерва ходит через HTTP со служебным токеном; предполагается, что резервирование не обращается к другим сервисам.
- Тест партий вызывает `StockPostingService.confirmPlacement` напрямую с готовым `SectionInfo`: проверяется именно
  конкурентное проведение (блокировка по ключу партии).
- Тест отмены использует настоящую БД request-service и заглушку `InventoryClient`; сообщения об ошибках проверяются по
  тексту («Отмена недоступна», «не найдена», «уже собрана»).
- Если тест `strictReservations_exactlyThreeOfFourSucceed` покажет другое число успехов, смотрите код ответа неуспешного
  резерва: тест считает успешными ответы 201.
