## 1. Текущее состояние

**Готово (этап 1).** Каркас в папке `frontend/` репозитория: Vite, React 18, TypeScript, Ant Design 5, React Router, TanStack Query.
- HTTP-клиент: токен, `X-Trace-Id`, разбор ошибок `{code, message, details, trace_id}`, `Idempotency-Key`, выход из сессии при 401 с кодом `UNAUTHORIZED`.
- Вход, выход, профиль, смена пароля. Токен в памяти и `sessionStorage`, срок из `exp`.
- Меню и маршруты по ролям из одного списка `src/layout/navigation.ts`; разделы пока заглушки.
- После любого входа открывается стартовая вкладка роли (заявки, задания или пользователи).

**Бэкенд, на который опирается фронтенд.** Готовы auth, catalog, warehouse, inventory, request, audit, notification, report (отчёты по движениям, поступлениям, выдачам, списаниям и комплектации). Не готовы отчёты по заявкам, расхождениям и остаткам.

## 2. Сквозные решения для всех этапов

| Тема | Решение |
|---|---|
| Структура | Новые разделы кладутся в `src/features/<раздел>/` (`api.ts`, `types.ts`, `hooks.ts`, `pages/`, `components/`). Общие вещи (статусы, форматирование, таблицы) в `src/shared/`. |
| Данные | TanStack Query. Ключи вида `['requests', filters]`. Каждая мутация инвалидирует связанные ключи. |
| Типы | Пишутся вручную по DTO. Если подключат springdoc (OpenAPI), перейти на генерацию через `openapi-typescript`. |
| Ошибки | Единый компонент `ErrorAlert`: `message`, `details` и `trace_id` (с кнопкой копирования). `CONCURRENT_MODIFICATION` показывает «Данные изменились» и кнопку обновить. `INVALID_STATUS_TRANSITION` обновляет карточку. |
| Idempotency-Key | Ключ создаётся при открытии формы или диалога действия и хранится в `useRef`. Сбрасывается после успеха. При повторе после сетевой ошибки отправляется тот же ключ. Обязателен там, где его требует бэкенд (раздел 4, этап 5). |
| Двойной клик | Кнопка действия блокируется на время запроса (`loading`). |
| Количества | Бэкенд принимает до 14 цифр целой части и 4 дробных. Поле количества: `InputNumber` с `precision` 4. Для единиц с `unitAllowFractions = false` только целые. Суммы округлять до 4 знаков. |
| Даты | В интерфейсе `toLocaleString('ru-RU')`. В фильтрах отчётов дата `yyyy-MM-dd`; в фильтрах движений `from/to` как ISO date-time. |
| Страницы | Нумерация с нуля (`page`), по умолчанию `size = 20`. Ant Design Table: `current = page + 1`. Не все списки постраничные: `/warehouses`, `/picking-tasks`, `/placement-tasks`, `/reservations`, `/requests/{id}/history` возвращают массив. |
| Имена вместо UUID | Склады из кэша `GET /warehouses`. Люди через `GET /directory/users?ids=` (доступно кладовщику и администратору). В позициях заявок, партий и документов названия товаров и коды секций уже приходят в ответе. |
| Статусы | Единый словарь `src/shared/statuses.ts`: русские названия и цвета для заявки, задания, поступления, списания и т. д. |
| Права | Скрытие кнопок и пунктов меню только удобство. Решение всегда за бэкендом: 403 ведёт на страницу «Недостаточно прав». |
| Безопасность клиента | Токен не в `localStorage`; никакого `dangerouslySetInnerHTML`; пароли не логируются. |
| Тесты | Vitest + React Testing Library для клиента, форм и логики кнопок; MSW для моков API; Playwright для сквозных сценариев (этап 8). |
| Размер сборки | Сейчас около 800 кБ. С этапа 3 маршруты подгружаются через `React.lazy`. |

## 4. Этапы

Размер: S (до нескольких экранов без сложной логики), M, L. Это относительная оценка, не сроки.

### Этап 2. Заявки пользователя и уведомления (USER) — размер M

**Экраны**
- **Список заявок:** `GET /requests` (фильтры `status`, `q`, пагинация). Колонки: номер, статус, приоритет, склад, создана, позиций.
- **Создание заявки:** склад (`GET /warehouses`, только активные), приоритет 0–9, комментарий (до 2000), позиции через `Form.List` (до 200): выбор товара с удалённым поиском `GET /products?q=&size=20`, количество, комментарий позиции (до 1000). Сохраняется как черновик (`POST /requests`), затем «Отправить» (`POST /requests/{id}/submit`).
- **Карточка заявки:** шапка, позиции (запрошено / одобрено / зарезервировано / выдано / нет в наличии), история статусов (`GET /requests/{id}/history`).
- **Действия USER:** изменить черновик (`PATCH`, позиции заменяются целиком), удалить черновик (`DELETE`), отправить, отменить с причиной (`POST /cancel`).
- **Колокольчик уведомлений:** `GET /notifications/unread-count` раз в 30–60 секунд (`refetchIntervalInBackground: false`), список `GET /notifications`, `POST /{id}/read`, `POST /read-all`. Клик по уведомлению ведёт в `/requests/{requestId}`.

**Зависимость от бэкенда:** переименовать поле `items` в `content` в `NotificationPageResponse` (иначе формат расходится со всеми остальными страницами).

**Готово, когда:** пользователь проходит путь «создать, изменить, отправить, отменить», видит историю и получает уведомления; ошибки валидации подсвечивают поля формы.

### Этап 3. Кладовщик: заявки, резерв, комплектация, выдача — размер L

**Очередь заявок.** `GET /requests` со всеми фильтрами (`status`, `warehouseId`, `requesterId`, `q`), имена заявителей через `/directory/users`.

**Действия по статусам** (кнопки строятся по таблице переходов из `RequestStatus.java`, решение остаётся за бэкендом):

| Статус | USER | STOREKEEPER |
|---|---|---|
| DRAFT | изменить, удалить, отправить | — |
| SUBMITTED | отменить | проверить (`review`), отменить |
| UNDER_REVIEW | — | отклонить (`reject`, причина) |
| APPROVED | отменить | зарезервировать, повторная проверка, отменить |
| PARTIALLY_AVAILABLE | отменить | зарезервировать частично (выбор количеств), отклонить, повторная проверка, отменить |
| RESERVED, RESERVED_PARTIAL | отменить | создать задание комплектации, отменить |
| PICKING | — | управление заданием, отменить |
| PICKED, PICKING_WITH_SHORTAGE | — | «Готово к выдаче» (`ready-for-issue`) |
| READY_FOR_ISSUE | — | выдать (`issue`) |
| ISSUED | — | закрывается автоматически |
| REJECTED, CANCELLED | — | закрыть (`close`) |

Отмена из PICKED и READY_FOR_ISSUE в бэкенде пока не реализована (шаг 1 плана и R3 в рисках). Кнопку добавить, когда она появится.

**Блоки экрана**
- Доступность перед резервом: `POST /reservations/availability` (запрошено / доступно / не хватает по позициям).
- Резервы заявки: `GET /reservations?requestId=` (секции, партии, количества).
- Резерв с частичным решением: диалог по позициям с `approvedQuantity` (`ReserveDto.items`).
- **Комплектация:**
  - создать задание: `POST /picking-tasks {requestId, workers[], autoAssignRemaining}`, работники из `GET /directory/workers`;
  - добавить работников: `POST /picking-tasks/{id}/workers`;
  - распределить строки, включая деление между работниками: `POST /assign-items` (ошибка `OVER_ASSIGNMENT` показывать у строки);
  - заменить или убрать работника: `DELETE /workers/{workerId}?replaceWith=&reason=` (причина обязательна);
  - прогресс: `GET /{id}/progress`, на экране по работникам и общий;
  - завершить: `POST /complete` (с `confirmShortage` и комментарием при недоборе).
- **Выдача:** диалог `issue` (получатель по умолчанию автор заявки, комментарий).

**Готово, когда:** через интерфейс проходит полный сценарий `scenario-5b.ps1` от отправленной заявки до закрытой.

### Этап 4. Работник склада — размер M

Экран мобильный в первую очередь: крупные кнопки и поля, меню сворачивается, одно действие на экран.

- **«Мои задания»:** две вкладки.
  - Комплектация: `GET /picking-tasks` (массив). Принять задание: `PATCH /picking-tasks/{id}/workers/{workerId}` (статус). Строки по секциям (код секции, партия, товар). Ввод собранного количества: `POST /picking-tasks/{id}/items/{rowId}/pick {pickedQuantity, comment}`. При недоборе комментарий. Общий прогресс, чужие строки не показываются.
  - Размещение: `GET /placement-tasks?status=`, подтверждение позиции: `POST /placement-tasks/{id}/items/{itemId}/confirm {sectionId, quantity, comment}`. Секция выбирается из `GET /sections?warehouseId=&q=`.
- **Остатки:** только чтение (раздел из этапа 5, доступен работнику).
- Сканирование штрихкодов на этом этапе не реализуется: поле ввода принимает код с внешнего сканера как набор с клавиатуры. Камера и ТСД зависят от штрихкодов секций в бэкенде (P1 в бэклоге фич).

**Готово, когда:** работник на телефоне собирает свои строки и подтверждает размещение; кладовщик видит прогресс обновлённым.

### Этап 5. Кладовщик: склад (приёмка, остатки, списания) — размер L

- **Поступления:** список (`GET /receipts`: `status`, `warehouseId`, `q`), создание (поставщик, внешний номер, дата, позиции с партией, сроком годности, характеристиками), правка черновика (`PATCH`, позиции заменяются целиком).
  - Рекомендация размещения: `POST /{id}/recommend-placement`. Таблица: стратегия, правило, секция, кандидаты со свободной вместимостью, пометки. Если `requiresStorekeeperAction`, нужен выбор секции.
  - Подтверждение: `POST /{id}/confirm` с решениями (другая секция или «Нераспределено»).
  - Задание на размещение: `POST /{id}/placement-tasks` (работник из справочника), отмена с причиной.
  - Статусы: DRAFT, RECEIVING, PLACEMENT, DONE, CANCELLED.
- **Расхождения при размещении:** `POST /placement-tasks/{id}/items/{itemId}/resolve` (принять фактическое или вернуть на размещение; комментарий обязателен).
- **Остатки:** `GET /stock` (`warehouseId`, `sectionId`, `productId`, `onlyAvailable`, `includeZero`); журнал `GET /stock/movements` (тип, документ, период, товар, секция).
- **Списания:** список (`status`, `reason`), создание (склад, причина `DAMAGED`/`EXPIRED`/`LOST`/`SCRAP`/`OTHER`, комментарий; для `LOST` обязателен), строки выбираются из остатков (`stockId` и количество не больше доступного). Кладовщик подтверждает (`/confirm`, **Idempotency-Key обязателен**), отменяет (причина). Если `approvalRequired`, сначала администратор нажимает «Одобрить» (`/approve`, этап 6).
- **Документы выдачи:** только просмотр (`GET /issues`, `GET /issues/{id}`). Выдача оформляется из заявки.
- **Не делать в интерфейсе:** ручной резерв (`POST /reservations`, `/release`) и прямое создание выдачи (`POST /issues`). Эти вызовы принадлежат request-service, а по плану безопасности (P1-10) для людей их закроют.

**Готово, когда:** сценарий «поступление, размещение, остатки появились» и «списание с подтверждением» проходят через интерфейс.

### Этап 6. Администратор — размер L

- **Пользователи:** список (`GET /users`), создание (логин `^[A-Za-z0-9._@-]{3,100}$`, пароль, ФИО, почта, телефон, роли из `GET /roles`), правка (`PATCH`: ФИО, почта, телефон, активность, набор ролей целиком), сброс пароля. Ошибки `LOGIN_ALREADY_EXISTS`, `LAST_ADMIN` показываются понятным текстом.
- **Каталог:** товары (поиск, фильтр по типу, архив/восстановление; SKU и единицу после создания менять нельзя), типы (создание, правка, активность), единицы (только создание, флаг дробных), атрибуты (только создание; тип STRING / NUMBER / BOOLEAN / REFERENCE с вариантами). Форма атрибутов товара строится по определениям.
- **Склады и секции:** склады (создание, правка названия, адреса, активности), секции (фильтры `warehouseId`, `status`, `q`, `zone`; создание и правка с ограничениями: размеры в мм, вместимость, типы товаров, материалы; статусы ACTIVE / BLOCKED / ARCHIVED). Ошибки `SECTION_CODE_EXISTS`, `UNASSIGNED_ZONE_PROTECTED`.
- **Правила размещения:** список, создание, правка (изменение увеличивает версию), история версий (`/{id}/versions`), признак резервного правила. Редактор условий строится по `RuleConditions` (`PlacementModels.java`).
- **Одобрение списаний:** очередь `GET /write-offs?status=DRAFT`, кнопка «Одобрить».
- **Аудит:** `GET /audit/events` (только ADMIN). Фильтры и колонки определить по `AuditController` (нужен файл, см. раздел 6).

**Готово, когда:** администратор создаёт пользователя, товар, склад, секцию и правило и видит их действие в сценарии приёмки.

### Этап 7. Отчёты — размер M

- **Готовые отчёты:** `GET /reports/stock-movements`, `/receipts`, `/issues`, `/write-offs`, `/picking/events`, `/picking/workers`. Фильтры: период (`from`, `to`), склад, товар, SKU, партия, номер документа, исполнитель, тип, номер задания, действие, пагинация. Имена людей подставляет сам сервис.
- Одна универсальная страница отчёта: описание колонок и фильтров в конфиге, таблица и форма фильтров общие. Формы строк берутся из `ReportDtos.java` и `PickingDtos.java` (уже есть в архиве экспорта).
- **Экспорт в CSV:** сначала по текущей выборке на клиенте (с ограничением на число строк). Серверный экспорт CSV/XLSX/PDF решается вместе с бэкендом (в бэклоге P2).
- **Отчёты по заявкам, расхождениям и остаткам:** экраны добавляются по мере готовности report-service.

**Готово, когда:** кладовщик и администратор получают все готовые отчёты с фильтрами и выгрузкой.

### Этап 8. Качество и выпуск — размер M

- Тесты: клиент (ошибки, 401, idempotency), формы заявки и списания, логика кнопок по статусам; сквозной Playwright-сценарий «поступление, заявка, комплектация, выдача» по четырём ролям.
- Ленивая загрузка маршрутов, проверка адаптивности (телефон для работника, планшет для кладовщика).
- Доступность: подписи полей, фокус в диалогах, управление с клавиатуры.
- Упаковка: Dockerfile (сборка и nginx), nginx проксирует `/api` на gateway и отдаёт SPA с запасным маршрутом на `index.html`; заголовки безопасности (CSP, `X-Content-Type-Options`); шаг в CI (`npm ci`, `tsc`, тесты, сборка).
- README фронтенда (запуск, переменные, соглашения), типы из OpenAPI, если подключат springdoc.
- **Refresh-токены.** Когда в бэкенде появится P1-8 (короткий access-токен и refresh), в клиенте нужен общий для всех запросов повтор после обновления токена (single-flight). Слой авторизации уже изолирован в `AuthContext` и `api/client.ts`.

## 5. Зависимости от бэкенда и плана безопасности

| Что | Когда нужно | Влияние на фронтенд |
|---|---|---|
| `NotificationPageResponse`: `items` → `content` | до этапа 2 | Иначе отдельная обработка формата уведомлений. Проверить `scenario-7-notifications.ps1`. |
| Правки gateway `application.yaml` (`issuer` на отдельной строке, URL уведомлений через переменную, удалить устаревший комментарий) | сейчас | Не влияют на работу интерфейса, но убирают ловушки. |
| P1-6: чтение секций и правил только для кладовщика, администратора (и работника для секций) | любое время | Совместимо: USER эти запросы не делает, работнику секции нужны. |
| P1-10: служебные токены, прямые вызовы резервов и выдач закрыты для людей | любое время | Совместимо: интерфейс их не использует (этап 5). |

## 7. Критерии готовности каждого этапа

- Все сценарии этапа пройдены вручную под нужными ролями; штатный путь не даёт 403.
- `npm run build` проходит без ошибок типов.
- Ошибки сервера показывают понятное сообщение и `trace_id`.
- Формы не отправляются повторно при двойном клике; операции с `Idempotency-Key` повторяются с тем же ключом.
- Для списков работают пагинация и фильтры, для длинных операций виден индикатор загрузки.
- Для разделов работника интерфейс удобен на телефоне.
- Обновлены этот документ (статус этапа) и README фронтенда.
